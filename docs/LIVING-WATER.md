# Living Water: Meaning, Evidence, and Implementation Boundary

**Living Water is the product's organizing metaphor for reality in continuous flow—not a claim that a diagram proves an event occurred.** The water vocabulary comes from the user's product vision. Engineering claims remain tied to observable records, provenance, authority, and verification.

## Lifecycle

```text
SOURCE → DROP → FLOW → CONTACT → OBSERVE → REFLECT → VERIFY → CHANGE → RECONCILE → REMEMBER → RETURN → NEW DROP
```

A drop may represent one intent, event, person, or object. Consequences ripple; continuity is a current; processes are streams; systems are rivers; the ecosystem is an ocean; changes are waves; observation is a mirror; context is depth; evidence brings clarity; uncertainty is turbidity; integration is confluence; disagreement remains divergence; loss is evaporation; and return is rain/renewal.

These are design meanings. They do not confer authority or establish external facts.

## Reality-bound rules

- A rendered or generated flow is not automatically a real-world flow: **beautiful flow ≠ true flow**.
- Preserve the distinctions `REPRESENTED`, `EXECUTED`, `OBSERVED`, `RECONCILED`, `VERIFIED`, and `REMEMBERED`. One does not imply the next.
- Missing evidence is `UNKNOWN`; an unattempted action is `NOT_EXECUTED`; a mismatch is `DIVERGENT`.
- Verification requires scoped expected/actual evidence and provenance. A stage named `VERIFY` is not itself verification.
- Authority must be explicit and scoped. A flow step cannot authorize a consequential action.
- Remembering requires a traceable source and lineage. A deterministic trace ID is not a durable memory ledger.
- Preserve divergence and uncertainty; never silently overwrite a prior account with a more convenient one.

## Current implementation: bounded v1 receipt

The current API returns `waterFlow` frames built by `buildOmegaWaterFlow` in `packages/mini/src/water-flow.ts`. The finite `omega.water-flow.v1` sequence remains:

```text
REALITY → ATTENTION → INTENTION → ACTION → CONSEQUENCE → OBSERVATION → LEARNING → RETURN
```

Each frame is deterministic local symbolic representation. Its provenance is `local-water-flow` with `verified: false`. It does not execute actions, observe the physical world, or establish durable memory. The web view now consumes the active command's actual v1 receipt, but treats mapped items as `MODEL_ONLY`; it shows unrepresented steps as `UNKNOWN` and an absent receipt as `NOT_EXECUTED`.

| Living Water concept | Current v1 relationship | Evidence boundary |
|---|---|---|
| SOURCE | Approximate relation to `REALITY` / state context | A context label is not independently sourced or verified reality. |
| DROP | `INTENTION` | Intent text is represented; this does not mean action was admitted. |
| FLOW | `ACTION` | A deterministic frame is a model, not execution evidence. |
| CONTACT | `CONSEQUENCE` | A possible ripple is not proof of external contact or impact. |
| OBSERVE | `OBSERVATION` | The frame is a modeled stage, not an observation receipt. |
| REFLECT | `LEARNING` | No human reflection is inferred from the stage label. |
| VERIFY | No distinct v1 water-flow stage | Verification must use a separate evidence-bearing result; v1 provenance remains unverified. |
| CHANGE | `ACTION` | The stage does not grant authority or prove a change occurred. |
| RECONCILE | No distinct v1 water-flow stage | Compare expected and observed state through the separate reconciliation path. |
| REMEMBER | No durable-memory event in v1 | A trace ID correlates this receipt only; persistence and lineage are not implied. |
| RETURN | `RETURN` | A modeled return is not a subsequent user intent. |
| NEW DROP | Not generated by v1 | A later intent must be a separate, attributable event. |

## Next evolution criteria

A future version can make these concepts first-class events only when each event has an attributable source, stable ID, sequence/parent lineage, bounded scope, timestamp where observed, and an explicit evidence state. `VERIFY`, `RECONCILE`, and durable `REMEMBER` need real evidence-bearing implementations, not optimistic defaults. New versions should preserve v1 compatibility or document the migration; no stage should be shown as completed solely because a deterministic model generated its label.
